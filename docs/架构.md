# 架构

## 分层

```
src/
├── cli.mjs            命令行入口（调用方之一）
├── core/io.mjs        抓取内核：HTTP(超时/重试/条件请求)、限速、并发池、原子写、日志
├── core/paths.mjs     产物路径约定（v2：源是路径维度，records/imagerefs 都带 <source>）
├── schema/index.mjs   数据契约：SCHEMA_VERSION、产物骨架、校验
├── sources/
│   ├── alioth/        玉璃（alioth.wiki）
│   │   ├── channels.mjs  频道表（声明"怎么抓"）
│   │   ├── harvest.mjs   频道抓取（索引 → 分片 → 落盘）
│   │   └── normalize.mjs 期规范化（版本排序 + 年份纠错）
│   ├── nanoka/         nanoka.cc：绝区零全部页面 + 原神/星铁非终局
│   └── registry.mjs    统一频道清单与按源分发（调用方只与这里打交道）
├── images/            图片层（与记录抓取解耦）
│   ├── refs.mjs          记录 → 图片引用 + 候选 URL（按源分派的资源名规则，唯一副本）
│   ├── store.mjs         下载 / 落盘 / 增量（URL + 体积判活，失败候选记录）
│   ├── harvest.mjs       按频道抓图（读已落盘记录，可只补某频道）
│   └── index.mjs         images.json 产物、entries 的 imageCount / icon 增强
└── export/index.mjs   产物汇总（index.json / periods.json / entries 图片元数据）
```

## 数据流

```
调用方（Atlas-Plugin / CLI）
  └─ 选定频道 id 列表 ──────────────► harvestChannels()
        │                                  │
        │                          每个频道：GET 索引（带 If-Modified-Since）
        │                                  ├─ 304 / 指纹未变 → 跳过
        │                                  ├─ 404 → absent（不删旧数据）
        │                                  └─ 变 → 抓分片 → 原子落盘 → 写 manifest
        ▼                                  ▼
   （插件决策）                      data/records/**
                                           │
                                    exportAll() → index.json + periods.json
```

## 职责边界（重要）

| 事项 | Hesperides | 调用方（Atlas-Plugin） |
|---|---|---|
| 有哪些频道 | 声明全量频道表 | 读 `plan`/频道表后自行筛选 |
| 抓哪些 | 只执行传入的 `ids` | **决定** |
| 何时抓 | 不知道时间 | `#图鉴更新` / 定时任务 |
| 增量还是全量 | 执行传入的 `mode` | **决定** |
| 失败后怎么办 | 记 `failures`/`absent`，保留旧数据 | 决定重试、降级、状态展示 |
| 产物格式 | 唯一真源（schema v2） | 只读 |
| 频道要不要裁剪 | **不裁剪**：覆盖上游全部页面 | 自行取舍 |

**Hesperides 不提供"默认抓取集合"，也没有频道开关**——`--all` 才是全部，其余都要显式点名。

### 供给原则（2026-11 明确）

- **不做业务裁剪**：与另一数据源重叠的页面（如 nanoka 的 gi 终局页）照样保留，不替消费者判断"这份数据有没有用"
- **多消费者**：Hesperides 不只服务 Atlas-Plugin；其他开发者可以自己选频道、自己决定用不用某份数据
- **只保证能力**：可抓、可增量、可续跑、可追溯（manifest 有 hash / 版本 / 时间）；用哪些、怎么组合，是消费者的事

## 为什么不用旧后端的结构

旧后端（`nanoka-atlas-backend`）把「采集器 + 数据格式 + 索引」揉在一起，索引只在运行结束一次性写盘、`incremental` 只是"读旧索引当底再全量重抓"，任何一次网络抖动都会让整轮白跑。Hesperides 的对应设计：

1. **每频道结束即写 manifest** → 中断可续跑
2. **索引未变即整频道跳过** → 稳态下每次更新只发 7 个请求
3. **失败不删旧数据** → 插件永远有可用读数（可能是旧的）
4. **多源一等公民** → 换源不动插件
