# 源适配

当前注册的数据源。**各源对等**：可抓的页面都抓、都保留，重叠部分不裁剪，
本仓库不判断谁更权威、也不替消费者选源——用哪些由调用方决定。

**源是可插拔的**：新增源（例如备用源，防现役源跑路）只需

1. `src/sources/<源>/` 下提供 `channels.mjs`（频道表）与 `harvest.mjs`（抓取器）
2. `src/sources/registry.mjs` 的 `SOURCES` 加一项 `{ source, channels, harvest, endgame? }`
3. 若该源有图片，在 `src/images/refs.mjs` 的 `SOURCE_IMAGE_RULES` 加一条 `{ assetBase, ext, gamePath, build }`。单游戏CDN没有游戏路径段时可声明 `fixedGame`，落盘时补齐该游戏

产物按 `<source>` 分段（`records/<game>/<source>/<page>/`），同名页不会互相覆盖；
导出、增量、图片去重、cleanup 都不需要为新增源改代码。`test/source-registry.test.mjs` 会校验注册项形状。

下表按覆盖面从大到小排列，不含主次含义。

| | nanoka.cc | 玉璃 alioth.wiki |
|---|---|---|
| 覆盖游戏 | 原神 / 星铁 / 绝区零 | 原神 / 星铁（`data/zzz/**` 全 404） |
| 记录形态 | dict（id → 对象），多语言字段 | 按频道类型各异（见下） |
| 版本 | 根 `manifest.json` 的 `latest` | 无根清单，版本在各期的 `Phases[].Ver` |
| 图片 | `static.nanoka.cc/assets/*.webp` | `img.alioth.wiki/*.png`（星铁路径段是 `sr`） |

## 一、nanoka.cc

### 端点

| 用途 | 地址 |
|---|---|
| 版本清单 | `https://static.nanoka.cc/manifest.json`（`[game].latest` / `live` / `available` / `new`） |
| 页面 | `https://static.nanoka.cc/{game}/{version}/{page}.json`（`{locale}` 取 `zh`） |
| 详情 | 同上，路径按 `detailEndpointPatterns`（`{id}` 占位） |
| 图片 | `https://static.nanoka.cc/assets/{game}/{目录}/{文件}.webp` |

### 频道形态

| kind | 含义 | 例子 |
|---|---|---|
| `single` | 单个 JSON 就是数据 | `nanoka:gi:diff` |
| `page` | 按 `ids` 键逐条落盘 | `nanoka:gi:character` |
| `phased` | 记录自带 `live_begin`/`live_end`，同时产出期索引 | `nanoka:zzz:boss` |

要点：

- 页面内容是 **dict：记录 id → 记录对象**（少数页为数组），记录字段多语言（`zh`/`en`/`ko`/`ja`）
- 数组页默认用元素自带的 `id` / `_id` 当记录键；**数值表**类页面（hsr 的 `EliteGroup` / `HardLevelGroup` / `InfiniteEliteGroup`）两者都没有，要在频道定义里用 `idFields` 声明组合键（如 `['HardLevelGroup', 'Level']` → `1_95`）
- 版本来自 manifest 的 `latest`，URL 里需要 `encodeURIComponent`（zzz 版本带 `+` 号）
- **zzz 终局页（`boss` / `shiyu`）的页面记录自带 `live_begin` / `live_end`** —— 绝区零终局期索引由此产出（旧后端没导出这层信息）
- 详情默认不抓；调用方传 `withDetails: true` 才逐条请求（CLI：`--with-details`）
- 页面 hash 与版本都没变才跳过；沿用 manifest 续跑语义
- 根清单快照会落盘到 `data/upstream/nanoka.json`，供消费端取 `latest`/`live`/`new`

### 覆盖范围

- 原神 / 星铁 / 绝区零**全部页面**，含与玉璃重叠的终局页
- 与玉璃重叠的页面**保留不裁剪**：gi 的 tower / rolecombat / leyline 期时间两处都有，由调用方取舍
  （Atlas-Plugin 这两个玩法取玉璃）；hsr 四个终局页的 `begin` / `end` / `live_begin` / `live_end` **全为空串**，期时间实际上只能从玉璃取到

### 图片规则

规则实现在 `src/images/refs.mjs` 的 `SOURCE_IMAGE_RULES.nanoka`：

```
https://static.nanoka.cc/assets/<game>/<目录>/<文件>.webp
```

- 扩展名 `.webp`（玉璃那边是 `.png`）
- 目录按「游戏 + 页面 + 字段」的启发式推，同一个资源可能落在两三个候选目录里，按序试、命中即止
- 绝区零的技能/按键图标是 `<IconMap:xxx>` 令牌，要先过 `ZZZ_ICON_MAP` 映射表

## 二、玉璃（alioth.wiki）

### 端点

| 用途 | 地址 |
|---|---|
| 数据 | `https://json.alioth.wiki/data/{game}/{lang}/{path}` |
| 文本 | `https://json.alioth.wiki/TextMap/{GI\|HSR}/{file}` |
| 图片 | `https://img.alioth.wiki/{gi\|sr}/{category}/{file}.png` |
| 图片缩放 | `https://transform.alioth.wiki/i/{同路径}?w=N&f=auto`（本引擎用原图，不走上游变换） |

- `lang` 用 **`ch` / `en` / `jp` / `kr`**（不是 `zh`），当前只取 `ch`
- 根级文件（`gi/banner.json`、`gi/GrowCurves.json`、`hsr/banner.json`、`hsr/eg.json`、`hsr/hlg.json`、`hsr/hsrboss.json`）**不带语言目录**
- 契约清单来自上游仓库 `alioth-wiki-code` 的 `data-directories.json`（本仓库文档里抄录一份；上游改结构时据它对比）
- **没有根清单**：版本信息分散在各期的 `Phases[].Ver`，所以 `data/upstream/` 下没有 `alioth.json`

### 频道类型

| kind | 含义 | 例子 |
|---|---|---|
| `single` | 单个 JSON 就是数据 | `gi:achievement`、`hsr:cw` |
| `phased` | 索引里 `Phases[]._id` → `{page}/{id}.json`，同时产出期索引 | `gi:abyss`、`hsr:as` |
| `ids` | 用选择器从索引取 id → `{page}/{id}.json` | `gi:monster`（`Templates` 字典键） |
| `static` | 固定文件列表 | `gi:tps`、`hsr:cw-categories` |
| `text` | TextMap 大文本 | `alioth:textmap:gi-readable` |

### ID 来源（2026-11 实测，非猜测）

| 频道 | ID 来源 |
|---|---|
| `gi:char` / `char-story` / `char-voice` | `char.json` 的 `Avatar[].ID` |
| `gi:char-gun` | `char.json` 的 `Gun[].ID` |
| `gi:char-flycloak` | `char.json` 的 `Flycloak[].ID` |
| `gi:weapon` | **`char.json` 的 `Weapon[].ID`**（没有独立的 weapon 索引） |
| `gi:relic` | **`char.json` 的 `Relic[].ID`** |
| `gi:monster` | `monster.json` 的 `Templates` 字典键 |
| `hsr:monster` | `monster.json` 的 `Templates[]._id`（数组数组） |
| `hsr:relic` | `char.json` 的 `Relic` 是"对象套数组"，取各数组的 `ID` |
| `hsr:cw-char` | `cw.json` 的 `Characters[]._id` |
| 终局 7 频道 | 索引 `Phases[]._id` |

### 覆盖范围

- **只有原神与星铁**（`data/zzz/**` 全 404）；绝区零页面由 nanoka 覆盖，本源没有
- 终局 7 个玩法：gi `abyss` 60 期 / `theater` 30 期 / `stygian` 13 期；hsr `chaos` 43 / `fiction` 28 / `as` 22 / `arbitration` 11
- 玉璃的 `Ver` 是**覆盖版本**，不换算成开启版本；期归属由调用方按 `begin` 判定

### 图片规则（2026-11 实测）

玉璃记录里的图片字段只有**资源名**（原神）或**带目录的相对路径**（星铁），不带完整 URL。
规则实现在 `src/images/refs.mjs` 的 `SOURCE_IMAGE_RULES.alioth`：

```
https://img.alioth.wiki/<gamePath>/<目录>/<资源名>.png
```

| 要点 | 结论 |
|---|---|
| 域名 | `img.alioth.wiki`（另有 `transform.alioth.wiki/i/…?w=N&f=auto` 提供缩放，本引擎用原图） |
| 游戏路径段 | 原神 `gi`；**星铁是 `sr`，不是 `hsr`**；玉璃没有绝区零 |
| 扩展名 | `.png`（nanoka 那边是 `.webp`） |
| 星铁的目录 | 记录值自带（`mostericon/…`、`monsterfigure/…`），注意 `mostericon` 是上游的拼写，少一个 n |
| 原神的目录 | 记录值只有资源名，按前缀推：`UI_MonsterIcon_`/`UI_ItemIcon_` → `MonsterIcon/`，`UI_AvatarIcon_` → `AvatarIcon/`，`UI_Img_LeyLineChallenge_` → `LeyLineChallenge/` |

两处反直觉但已实测确认：`UI_ItemIcon_*` 也放在 `MonsterIcon/` 目录下；幽境危战的展示图单独占 `LeyLineChallenge/`（单张约 300 KB）。

**落盘归一**：URL 里的 `sr` 段在产物路径里统一写成 `hsr`（`images/hsr/mostericon/…`），否则同一游戏的图会被拆成两个目录。

### 已知上游缺陷（都被规范化处理或可容忍）

| 现象 | 例子 | 处理 |
|---|---|---|
| `Time` 年份写错 | 危战 6.4~6.7 写成 2025（应为 2026） | `normalize.mjs`：期序按 `Ver` 排，begin/end 做年份修正并标 `timeCorrected`，原值留 `rawTime` |
| `end` 早于 `begin` | 危战 6.4 `2026-03-04 ~ 2025-04-07` | 同上，end 加年 |
| 契约有、线上没有 | `hsr/hsrboss.json` 返回 404 | 频道状态 `absent`，不算失败、不删旧数据 |
| 数据超前 | 已入库 gi 7.3、hsr 4.7-4.8 | 「本期」必须按 `begin ≤ now ≤ end` 判，不能取 `Phases[0]` |

## 三、Lunaris

| `lunaris:gi:weapon` | `<version>/weaponlist.json` | `<version>/chs/weapon/<id>.json` |
| `lunaris:gi:artifact` | `<version>/artifactlist.json` | `<version>/chs/artifact/<id>.json` |
| `lunaris:gi:item` | `<version>/materiallist.json` | 目录保留原字段 |
| `lunaris:gi:monster` | `<version>/monsterlist.json` | `<version>/chs/monster/<id>.json` |
| `lunaris:gi:tower` | `<version>/towerlist.json` | `<version>/chs/tower/<id>.json` |
| `lunaris:gi:rolecombat` | `<version>/roleplaylist.json` | `<version>/chs/roleplay/<id>.json` |
| `lunaris:gi:tutorial` | `<version>/tutoriallist.json` | `<version>/chs/tutorial/<id>.json` |
| `lunaris:gi:achievement` | `<version>/achievementlist.json` | `<version>/chs/goals/<id>.json` |

| `lunaris:gi:event` | `<version>/eventlist.json` | 目录保留原字段 |

| `lunaris:gi:leyline` | 官网 `data/leylinechallenge/<id>.json` | 完整期记录 |

最后两类从官网域名取文件，可以独立于API版本清单采集。幽境期号5269001～5269013来自本次官网已发布的频道表，新增期号需随官网更新。当前7.2.51的chapterlist返回404，按 `absent` 记录并保留旧产物。目录在其它版本的可用性取决于上游。

目录原始字段保留，中文名从 `chsName` 等字段抽取到labels，稀有度按qualityType映射。`withDetails` 增加 `detail`，失败时保留旧详情并记录error供恢复。由无详情切换为带详情、版本变化或新增记录时会重新补齐覆盖。每频道结束原子保存manifest，健康304和同hash跳过，失败后可在相同目录内容下续抓。

深渊、剧诗与幽境分别取openTime/closeTime、beginTime/endTime、scheduleStartTime/scheduleEndTime，保留显式秒级时刻。期表按源输出到 `games.gi.lunaris`。源之间同名页独立保存，消费侧选择使用哪一源。

图片根为 `https://api.lunaris.moe/data/assets`。远程路径没有游戏段，落盘归为 `images/gi/<目录>/<资源>`。图片规则按官网目录与字段生成，角色主图、武器、圣遗物、材料及详情技能等字段参与既有图片流程。原字段与目录关系见 `SOURCE_IMAGE_RULES.lunaris`。跨源候选沿用格式偏好，Lunaris的webp加入现有webp组。

## 四、Gensri

公开数据库与幽境危战采用同一 `gensri` 源，覆盖原神四个频道。2026-11-14 目录实取为 133 个角色文件、249 件武器、68 套圣遗物和 5 期幽境危战。[数据库](https://db.gensri.wiki/) / [幽境危战](https://www.gensri.wiki/985/)

| 频道 | 目录 | 详情 |
|---|---|---|
| `gensri:gi:character` | `db.gensri.wiki/data/characters.json` | `/data/characters/<版本映射file>.json` |
| `gensri:gi:weapon` | `db.gensri.wiki/data/weapons.json` | `/data/weapons/<版本映射file>.json` |
| `gensri:gi:artifact` | `db.gensri.wiki/data/artifactlist.json` | `/data/artifacts/<版本映射file>.json` |
| `gensri:gi:stygian` | `www.gensri.wiki/985/data/seasons.json` | `/985/<season.page>config.json` |

### 记录键与最新详情

数据库记录优先以目录 `file` 为键，随后使用 `setId`、`id`。角色目录 133 个 file 对应 127 个数字 id，旅行者七元素共用 `id=10000005`，各元素的 `10000005_<ELEMENT>` 文件分别保留。名称取目录 `name` 或 `chsName`，稀有度取目录 `rarity` 或 `qualityType` 的白绿蓝紫橙映射，导出到现有 `entries.name/rarity`。

一批数据库采集读取一次 `/data/versions.json`。详情优先 `versions[characters|weapons|artifacts][稳定键][0].file`，映射缺项时使用稳定键。实测 `10000147@7.2.51` 和 `12438@7.2.51` 对应当前详情，裸文件仍是旧版。原目录字段和详情分别保存，`sourceMeta.catalogFile`、`requestedDetailFile`、`detailFile`、`detailVersion` 记录稳定键、本轮目标与成功落盘的实际出处。远端详情失败时保留旧详情和旧实际出处，本轮目标照常记录，下一轮继续补齐。

### 增量与期表

数据库同时比较目录 hash、当前版本和该类文件映射 hash，详情模式首次启用、版本映射变化或此前详情失败时重新读取目录。健康频道沿用 Last-Modified 条件请求与同 hash 跳过。目录键及形状在写入前一次校验，404、坏 JSON、重复键保留旧记录。

幽境频道独立读取期目录。`startAt/endAt` 按官网东八区时刻转换为含秒和 `+08:00` 的字符串，保留官方版本和全部五期，导出时沿用现有期开启时间排序。2026-11-14 的有效期是 `st072`，首条 `st073` 将在 12 月 23 日开始。消费端按起止时间选择当前期。

### 图片

图片规则复现官网前端的主图地址。角色目录 `image` 保留 `/png/Characters/` 自定义路径，否则使用 `/png/Characters/db/<数字id>.webp`。武器目录 `image` 和详情 `weaponIcon` 使用 `/png/Weapons/db/<id>.webp`，套装 `setIcon` 使用 `/png/Artifacts/<setId>.png`。技能等其他图片字段沿用自身值。显式 `/png/` 相对路径在幽境页解析到 www 域，其余页解析到 db 域。

`SOURCE_IMAGE_RULES.gensri` 使用 `normalize` 在绝对 URL 短路前处理官方主图覆盖，`fields` 纳入 camelCase `weaponIcon/setIcon`，`assetBases` 声明 www 资源域。两个域均以 `fixedGame: 'gi'` 落盘，保留 Characters、Weapons、Artifacts、Enemies 目录隔离。原三源的普通资源名候选相对顺序保持。

采集已接入注册表和显式 CLI。Atlas 消费端仍按自己的源选择和字段转换处理 Gensri 原始记录，985 的机制、两档生命值等内容可从 `record.detail` 读取。

## 五、各源共有

### 候选顺序（重要）

同一资源被多个源引用时，候选顺序按**格式偏好**排（当前是 nanoka / Lunaris 的 `.webp` → 玉璃的 `.png`），与记录所属源无关。

**排序依据是格式体积，不是源的等级**——webp 通常比 png 小，所以同一条资源优先进 webp。
若各按「记录所属源优先」，同一条资源会落成 `<名>.webp` 与 `<名>.png` 两份
（实测某次全量多存 1,319 个 / 150 MB）。

统一之后，各源命中的是同一个 URL，落盘路径一致、天然去重；
玉璃独有的资源（幽境危战展示图等）nanoka 候选为空，自然回落到 png——这不是"降级"，
只是那条资源本来只有 png 版本。

### 合规

- 数据抓取自公开站点，仅供本地自用；**不随仓库分发**（`data/` 在 `.gitignore`）
- 抓取限速：并发默认 4，分片间隔 100~220ms 抖动，UA 标明 `Hesperides/<ver>`（版本号取自 `package.json`）
- 引用仓库自身代码（Nuxt 前端）与数据版权归原作者；本仓库只实现抓取与规范化
