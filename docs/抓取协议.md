# 抓取协议

## 接口

```js
// 供调用方（Atlas-Plugin）使用；CLI 也走这两个
harvestChannels(channels, { dataDir, mode, concurrency, onChannel })
harvestChannel(channel, { dataDir, mode, concurrency, previous, fetchImpl, delay })
```

- `channels`：频道定义数组（来自 `sources/alioth/channels.mjs`，调用方自行筛选）
- `mode`：`incremental`（默认）/ `full`
- `previous`：上一轮的 manifest 片段，由 `harvestChannels` 从 `manifest.json` 取出并传入

**本模块不读环境变量、不读插件配置、不跑定时任务**——抓取时机与范围完全由调用方决定。

## 增量模型

| 频道类型 | 判据 | 行为 |
|---|---|---|
| 全部 | 索引 `If-Modified-Since` → 304 | 整频道跳过 |
| 全部 | 索引内容指纹与 `manifest.indexHash` 相同 | 整频道跳过（上游不给 304 时兜底） |
| `phased` | `phaseVersions[id] !== 当前 Ver` | 只抓变化的期 |
| `ids` / `single` | 索引变了 | 整批重抓（版本更新时条目普遍变化） |
| `static` / `text` | 每个文件的指纹 | 只重写变化的文件 |

稳态成本：索引未变时，一次更新只发 7 个请求（终局频道各 1 个）。

nanoka 源额外两条：

- 页面 URL 带版本段，版本取根 manifest.json 的 latest；**hash 与版本都没变**才跳过
- 详情请求只在调用方传 withDetails: true 时发起（CLI 对应 --with-details），默认不抓

## 状态语义

| status | 含义 | 是否保留旧数据 |
|---|---|---|
| `ok` | 本轮成功（`failed>0` 为部分失败） | 是 |
| `skipped` | 内容未变 | 是 |
| `absent` | 上游 404（契约有、线上无） | 是 |
| `failed` | 索引失败或整批条目失败 | 是（manifest 不覆盖旧记录数） |
| `unverified` | 尚未验证 ID 来源 | 是 |

**任何状态都不删旧数据**；插件据此决定展示「数据截至」还是报错。

## 写盘与续跑

1. 每条记录 / 每个文件：同目录临时文件 + `rename`
2. **每个频道结束就写一次 `manifest.json`** → 进程被杀后重跑只补没抓的
3. 导出（`index.json` / `periods.json`）在所有频道结束后统一生成，也可单独 `--export` 重建；v2 起按 `<game>/<source>/<page>` 分组

## 限速

- 索引请求：串行（每频道 1 次）
- 分片请求：并发 `concurrency`（默认 4），每次请求后 `100~220ms` 随机间隔
- 重试：最多 2 次，线性退避；超时 20s
- UA：`Hesperides/<ver> (+repo)`

## 期规范化

见 `src/sources/alioth/normalize.mjs`：

1. 期列表按 `Ver` 排序（同版本按 `begin`）
2. `begin` 早于前一期 → 尝试 +1/+2 年，取保持单调的最小修正
3. `end` 早于 `begin` → 同样加年
4. 被修正的期标 `timeCorrected: true` 并保留 `rawTime`

## 命令行

```bash
node src/cli.mjs --list-channels
node src/cli.mjs --channel alioth:gi:abyss
node src/cli.mjs --channels alioth:gi:abyss,alioth:hsr:as --mode full
node src/cli.mjs --all
node src/cli.mjs --all --images --with-details    # 全量记录 + 详情 + 图片（首次建库）
node src/cli.mjs --channels nanoka:hsr:lightcone --images   # 只补某频道的图
node src/cli.mjs --export
node src/cli.mjs --verify
node src/cli.mjs --prune-images          # 预览：同资源多格式的重复文件能省多少
node src/cli.mjs --prune-images --yes    # 真删（修正 imagerefs → 刷新 index 投影 → 再删图）
```

退出码：`0` 全部成功 / `1` 有失败或校验不过。`--json` 输出机器可读摘要（含 `images` 小计）。

### 图片

- 记录抓完后单独一遍：`--images`，与记录抓取解耦，可只补某些频道
- 一个远程 URL 只落一个文件（按 URL 去重），路径镜像 CDN；扩展名以 content-type 为准
- URL 规则按源分派（见 `docs/源适配.md` 的「图片规则」）：玉璃用 `img.alioth.wiki`，nanoka 用 `static.nanoka.cc/assets`；落盘时 URL 里的游戏路径段归一成 gameId（玉璃星铁的 `sr` → `hsr`）
- 增量：URL + 本地文件体积判活（`--verify` 时再比 ETag），候选失败记进 `images.json` 的 `failures`，下一轮默认不再探测
- **上一轮未完成（`failed` 或带 `error`）时不走条件请求、不做同 hash 短路**：否则上游恢复后索引没变 → 直接 `skipped`，缺的记录/详情永远补不回来。这类频道下一轮强制重抓，成功后才恢复 304/同 hash 跳过
- **期版本只对成功落盘的期前进**：失败期不写新 `phaseVersions`，下一轮才会重试；已落盘的旧文件保持原样
- **详情失败保留旧 `detail`**：只更新摘要，并把失败写进 `error` 驱动重试；HTTP 200 但内容解析不出来也算失败（不能用空对象擦掉旧详情）
- **图片按引用级并发、候选逐个试**：一条引用命中第一个可用候选即停，跨引用相同 URL 共享同一个 Promise（只请求/写盘一次）
- **退出码覆盖条目级失败**：频道状态可能是 `ok` 但内部有条目 503，此时 `summary.failed` 仍是 0。CLI 的退出码同时看「频道失败」与「任何频道的 `result.failed > 0`」，调用方（插件）才能据此重试
- **同 URL 校验失败后不许从资源键绕回**：体积或 ETag 校验已拒绝的旧缓存，不能再被「按资源键复用」兜回来（否则 `verify` 明明看到新 ETag、GET 却是 0 次，文件保持旧内容）
- 去重：按 **URL** 落盘，但候选顺序固定 **nanoka（webp）→ 玉璃（png）**，与记录所属源无关——这样两个源引用同一资源时命中的是同一个 URL，落盘路径一致、天然去重
- 历史遗留的多余格式用 `--prune-images` 清理：同 `<目录>/<基名>` 只留首选扩展名（webp > png > jpg > …），删前校验首选非空
- **清理顺序**：先改写 `imagerefs` 里指向被删文件的 `localPath`（同时同步 `bytes`、清空 `etag`）→ 再 `exportAll()` 刷新 `index.json` 的 `entries.icon` → **最后**才删旧图。任一步失败旧图仍在，引用不会悬空；顺序反了会出现「图片文件已删、索引图标仍指着它」
- 候选逐个回退：一个资源常有 2~6 个 URL 猜测（上游目录命名不统一），命中即止
- 全部候选都 404 → 落占位图并标 `placeholder`，不删旧数据

## 304 与增量

nanoka 页面与玉璃索引都发条件请求（`If-Modified-Since`）；上游回 **304 按 `skipped` 处理**（沿用上一轮记录与 manifest），
**不能当失败**——否则每次增量都会把整频道标红。
