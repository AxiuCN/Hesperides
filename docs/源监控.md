# 源监控（CI）

用 GitHub Actions 每天/每周跑一次**完整重抓**，只回答两件事：**源还活着吗**、**条数有没有异常**。
产物写临时目录，不入库、不缓存、不与线上数据混用。

## 两档任务

| 工作流 | 时段（UTC / 北京） | 范围 | 频道 | 请求量级 | 体积 | 超时 |
|---|---|---|---|---|---|---|
| `source-monitor-daily.yml` | `23 1 * * *` / 09:23 | `runtime`：nanoka 全量 + 玉璃终局（**与 `#图鉴更新` 同口径**） | 72 | ≈274 | ≈82 MB | 30 分钟 |
| `source-monitor-weekly.yml` | `47 2 * * 1` / 周一 10:47 | `all`：全引擎 records-only，跳过 TextMap | 135 | 数千 | 数百 MB | 90 分钟 |

时段是刻意选的：北京 09:23 在上游 18~20 点（UTC+8）更新高峰之后、也在 Bot 5:00 日更之后，
既不和人工拉取抢上游，也不和日更撞车；周任务再错开 1.5 小时。

**不要用整点**：GitHub 的 `schedule` 是尽力而为，整点（尤其 `00:00 UTC`）最拥堵——
实测 `0 0 * * *` 的日任务在 2026-11-17 被推迟到 `07:13Z`（晚了 7 小时 13 分，job 本身只跑了 58 秒）。
如果要准点，只能靠外部定时器打 `workflow_dispatch`（或干脆放服务器计划任务），GitHub 自身不保证时间。

## 判定口径

只有三条，不做漂移阈值、不存历史基线：

- 🔴 **红**（job 失败 + 建 issue）：CLI 退出码非 0、有频道 `failed` / `absent`、频道没写进台账
- 🟡 **黄**（job 仍成功）：某频道 `records = 0`
- 🟢 **绿**：其余情况，把「频道 × 条数」照表记进 step summary

网络抖动兜底：整体失败时等 30 秒重试**一次**，只一次——重试多了等于把上游当靶子。

## 本地复跑

```bash
node tools/validate-sources.mjs --scope runtime            # 每日档同口径
node tools/validate-sources.mjs --scope all                # 每周档同口径
node tools/validate-sources.mjs --scope runtime --data-dir ./data-probe --json
```

退出码 `0` = 绿或黄，`1` = 红；结果 JSON 写系统临时目录的 `hesperides-monitor.json`，
CI 里另外写 `$RUNNER_TEMP/hesperides-monitor.md` 与 step summary（失败时直接作为 issue 正文）。

## 边界

- **不含详情与图片**：`--with-details` 会让请求数按记录数翻倍，`--images` 一次约 660 MB——
  两者都不适合每天跑，图片形状几乎不变，抽一张看 `content-type` 即可。
- **不验证产物可用性**：那是 `--verify` 的事，抓完顺带跑一遍更划算（必要时在 workflow 里加一条）。
- 该监控只覆盖「频道还活着 + 条数没塌」，真实详情质量、图片可用性、Bot 侧渲染仍需部署环境验收。
